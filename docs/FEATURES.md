# Feature inventory

Caskrun aims to cover the **publicly documented CrossOver Mac workflows** with original code and independently licensed runtimes. This checklist is a requirements map, not a claim of compatibility or parity. It draws on public CodeWeavers documentation only; CrossOver code, assets, installer recipes, and bundled runtime do not belong in this project.

Statuses distinguish source implementation from installer, client, authentication and game validation. **Present in source** means a code path exists. **Partial** means only part of the workflow exists. **Planned** means no implementation exists. The current local candidate contains an ARM64 SwiftUI app/core and independently built Wine 11.0 with GnuTLS, original Steam CEF/Dock changes and general per-executable native identities. Its source and runtime receipts accompany the ignored development package; it remains ad-hoc signed.

The [MaPC/MacadeKit adaptation](AUTOMATIC_GRAPHICS_AND_STORES.md) adds bounded
static graphics detection for Automatic and EA/Ubisoft installed-game discovery
and publisher launch requests. Saved manual renderers remain authoritative;
a running bottle keeps one renderer until its next idle launch. These source
improvements do not establish additional launcher sign-in or gameplay support.

Collection groups Windows apps and locally installed Steam/Epic/GOG games into named bottle folders, alongside browser shortcuts and explicit PS5 imports. The floating capsule has Collection, Discover and a + menu; one compact filter menu selects platform and Games/Apps. Single-click opens a bottle folder and its right panel; double-click opens the primary app. Closing the panel returns to the root collection. Inside a folder, double-click opens the selected item. Bottle management remains in the right panel and Command-3. Discover offers eight experimental Windows installers and browser links. Library and Game reports remain absent. The included Windows engine is selected automatically, with no global Settings screen. The integrated KytyPS5 adapter is optional and experimental; a user-selected engine is required, and gameplay through that adapter is unvalidated. Separately, the AnyPS5/Wine experiment ran public PS5 DOOM homebrew with rendering, input, save/load and relaunch verified; that route is not integrated into the app. See [AnyPS5 results](ANYPS5_WINE.md).

Earlier user-led Steam tests reached a usable sign-in window and one working Dock icon, with intermittent black relaunches and reported low visual quality. High Resolution passed isolated registry/API probes and later sharpness measurements on Steam and Wine builtin windows; DPI-unaware installers can remain upscaled. It stays optional and off by default. The October round completed GOG, Battle.net, Ubisoft and itch.io setup but found unusable clients; Epic's MSI failed and EA was closed at its agreement. Rockstar setup started but window inspection was blocked; its test was canceled and cleaned. Those isolated launcher tests did not verify authentication or gameplay. On 16 October 2026, the user confirmed that R.E.P.O. launched and worked with DXMT in an imported Steam bottle. This does not validate the complete fresh-install/sign-in/download/replay journey or broad game compatibility. Camp Forest Green's Steam missing/not-logged-in error has recurred; its game reports Steam API initialization failure despite Steam being signed in and connected, and the cause remains unresolved. The [launcher validation record](LAUNCHER_VALIDATION.md) is the current stage-by-stage evidence; older smoke results below retain their original scope.

The preceding maintenance phase passed 375 Rust unit tests and 6 integration tests, with 2 existing tests ignored; 97 Python checks and 10 Swift argument checks also passed. The library phase adds focused browser privacy, compatibility-data, manifest-discovery and Steam-install-request checks. The optional [DXMT controls](DXMT_OPTIONS.md) have a separate passing original x64/x86 API matrix; [app integration](DXMT_APP_INTEGRATION.md) retains its loader, rendering and migration evidence. See [maintenance workflows](DEMO_MAINTENANCE.md) and the [manual checklist](MANUAL_TEST_CHECKLIST.md). Source and graphics API tests do not establish app/game compatibility. The [implementation plan](COMPATIBILITY_PLAN.md) describes remaining work, while [UI smoke](UI_SMOKE.md) records earlier visual/navigation checks.

Reviewed Steam bottles can skip the earlier TLS/Steam engine releases when
moving to the switchable DXMT package. These exact upgrades retain the Steam
recipe, PE, idle, backup and runtime verification guards. During full Quit,
a mismatched recorded predecessor is used only after a separate full-package
hash matches its recorded identity and the shared reviewed-package allowlist.
If an app update replaced that exact canonical package location with a reviewed
direct successor, shutdown can instead prove the bottle is already idle: it
only waits on the existing Wine server and checks current file owners. It
does not send a stop request, change the runtime record, create a migration
backup or repair bottle configuration. A running or unverifiable old session
still prevents this idle-only exit. Missing, custom and unknown packages remain
errors. Shutdown clears inherited loader
and library overrides, retains the user's server lookup context and sets the
exact bottle paths. This does not migrate the record or establish compatibility
with unreviewed engines. The existing race between checking a user-writable
package and executing it is not eliminated; the trailing metadata recheck
shares that limitation. Recorded predecessor packages must remain at real,
canonical paths. Symlinked or missing packages fail closed with an error;
shutdown does not automatically repair their paths.

## Discover and install

The Steam setup follow-up prepares Valve's current, unmodified Windows x64
bootstrap before the first client launch, with bounded downloads, publisher
manifest checks, executable-format checks and an atomic replacement after
target and idle-state rechecks. Cancellation before replacement preserves the
original executable; replacement is not an automatic rollback protocol.
Steam retains its normal updater, sign-in and ownership checks. The app waits
for a main-sized, onscreen Steam window owned by that bottle's generated native
identity before hiding Caskrun; a spawned process alone does not finish the
handoff. Startup feedback prevents repeated Open requests, and
**Stop waiting** ends only that observation so Caskrun's controls return while
Steam stays running. A timeout keeps successful setup intact and reports
startup feedback instead of offering to repeat a completed installer. The
wait has a finite deadline and needs neither
Accessibility nor Screen Recording permission. Steam update phases and download
percentages come only from complete new events in its bottle-local bootstrap
log, with bounded reads and symlink refusal; old sessions and elapsed time alone
never become update progress. Other catalog stores use the same bounded window
handoff and Stop waiting controls with neutral startup text, without assuming
Steam's updater behavior. Count-only local diagnostics help investigate window
matching without recording names, identifiers, paths or window titles. These
changes are implemented in source; 100 focused Swift checks and full app
typechecking passed. Packaged
installation, account sign-in and gameplay acceptance remain separate checks.
Temporary files are cleaned on normal success, handled failure and cancellation;
cleanup after an abrupt process or system crash is not guaranteed.
Keep one current reviewed runtime package and one current installer/checksum;
generated test files and superseded build copies are disposable after owner
checks. See [fresh Steam startup evidence](LAUNCHER_VALIDATION.md#fresh-steam-setup-and-startup-feedback).

## Release gates

1. **Working baseline:** an independently sourced Wine runtime starts; Caskrun initializes a real bottle, installs a small unlisted EXE and MSI, waits for completion, shows logs, and relaunches the installed program.
2. **Catalog workflow:** Steam and other supported entries get original, tested installation recipes, verified download sources, dependency handling, cancellation, and honest compatibility notes. Users can still choose any local installer.
3. **Bottle and app management:** implement and test launcher discovery, bottle lifecycle actions, backup/restore, and diagnostics above.
4. **Compatibility and release:** test Apple Silicon, including Windows x86/x64 apps, macOS integration, graphics/input options, accessibility, dependency licensing, signing/notarization, and DMG installation. Mark a row **Validated** only with repeatable evidence.

## Explicit non-goals

- No CrossOver trial, purchase, activation, account, or license-expiry flow. Caskrun is a separate open-source product.
- No assertion that public documentation lists every internal CrossOver feature or that Caskrun can run every Windows app. Compatibility depends on the runtime, macOS, hardware, and the application.
