_Historical research snapshot: 23 September 2026. Independent Wine 11.0 source builds were staged in relocatable **development-only** packages inside ignored `.build/`. The then-current local app/DMG included a fresh upstream Wine build with GnuTLS and two original Steam CEF/Dock patches, plus source/patch receipts. Its latest packaged Steam UI retest was pending. Those artifacts were ad-hoc signed; no Developer ID, notarization or game acceptance was established. One separate prebuilt archive was inspected without running it._

## Historical baseline decision

Keep Caskrun's launcher independent of CrossOver. The local development build uses **fresh, pinned upstream Wine 11.0 source** inside Caskrun.app and runs it as a separate x86_64 process under Rosetta. Its two reviewed Caskrun patches add Steam-only CEF helper flags and native Dock identity; they leave Steam's binaries untouched. Keep the engine automatic for users; the app has no Wine picker or Settings screen. Validate the full runtime before public distribution or automatic updates. Caskrun's MIT source and packaged Wine binaries and patches retain their respective licenses and notices. ([patch record](../runtime-patches/README.md))

Wine 11.0 is a reasonable stable baseline: Wine announced its source tarball and completion of the new WoW64 architecture in January 2026. WoW64 can run 32-bit Windows programs in a 64-bit Wine setup, but that claim still needs validation for our exact macOS build and target apps. [Wine 11.0 release announcement](https://list.winehq.org/hyperkitty/list/wine-announce@list.winehq.org/thread/MXULWEMXQ5C24UEJ2STHPIUHNOZ7AZPQ/)

Do not prescribe `brew install --cask wine-stable` as our setup path or bypass Gatekeeper to use it. Its `Contents/MacOS/wine` wrapper and bundled Wine binary are x86_64. The wrapper has no code signature; the Wine binary has only an ad-hoc signature, with no Developer ID team. This confirms the archive is unsuitable as a notarized, ready-to-distribute Caskrun runtime. No Wine binary was executed or installed, and the inspection copy was removed afterward. [GStreamer cask](https://github.com/Homebrew/homebrew-cask/blob/HEAD/Casks/g/gstreamer-runtime.rb)
- **Historical September experiment:** an [independent Wine 11.0 source build](WINE_BUILD_EXPERIMENT.md) ran under ignored `.build/`. Project-local GNU Bison 3.8.2 and x86_64 FreeType 2.14.3 passed Wine's configure checks. `make -j8` and `make install` produced an x86_64 macOS loader and i386/x86_64 PE components; `wine --version` reported `wine-11.0`. - A fresh WineHQ 11.0 source tree was built with the pinned Caskrun [Steam CEF and Dock patches](../runtime-patches/README.md), plus the independent GnuTLS/FreeType/Mono/Gecko inputs. The source build and package scripts pin Wine's SHA-512, both patch SHA-256 values, and the Steam loader plist SHA-256; the development package contains the exact Wine source archive, patch files, loader template, licenses, and `source/SOURCES.txt`. The current local app/DMG contains that package and a native Steam loader alias. A disposable patched-Wine prototype rendered a usable sign-in window and one Steam Dock item whose click restored focus. The exact patched package still needs a live Steam UI test from the migrated app/DMG; no account sign-in, game, or public release behavior was verified. ## Prebuilt Wine archive feasibility

The [Gcenx macOS Wine builds](https://github.com/Gcenx/macOS_Wine_builds) are separately maintained **Wine builds**, not CrossOver app code. The maintainer distributes `.tar.xz` files and documents unpacking a `Wine *` app bundle and moving it to `/Applications`; project-local relocation is **not documented as supported**. The package is configured for `x86_64-apple-darwin` and uses MacPorts libraries. The current release notes require an all-user `GStreamer.framework` and include shared Wine Gecko and Wine Mono. [Maintainer README](https://github.com/Gcenx/macOS_Wine_builds/blob/master/README.md), [11.17 release](https://github.com/Gcenx/macOS_Wine_builds/releases/tag/11.17)

**Security/relocation conclusion:** The stable archive was safe to *download for inspection* into Caskrun's ignored `.build/` directory, but its unsigned wrapper and ad-hoc signed Wine binary do not establish a Developer ID signed or notarized runtime. We cannot yet say it can be **run** from a project-local path while preserving standard macOS security. Homebrew disabled the related Wine casks after Gatekeeper checks failed, and the required GStreamer framework is missing and documented as a system-wide install. The full bundle's Gatekeeper assessment and project-local execution remain untested. Do not remove quarantine flags, disable Gatekeeper, or silently install a framework merely to make this archive run. Apple's distribution guidance calls for valid signatures and notarization, and documents `codesign`/`spctl` checks. [Apple notarization guidance](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple assessment commands](https://developer.apple.com/documentation/security/resolving-common-notarization-issues)

**Remaining non-executing preflight before any future run:** if reevaluating the stable archive, download it again into `.build/wine-probe/` and repeat the pinned SHA-256 check. Inspect the complete bundle with `codesign --verify --deep --strict --verbose=2`, `codesign -dv --verbose=4`, `spctl --assess --type execute --verbose=4`, and `file`/`otool -L` on the Wine binaries and dependent libraries. Check for `/Library/Frameworks/GStreamer.framework` without installing it. **Stop before execution if Gatekeeper rejects it or required libraries are absent.** Only after those checks pass should a disposable `WINEPREFIX` under `.build/wine-probe/` be used to test `wine --version`, `wineboot --init`, and relocated bundle resources. These execution tests have not been run. The source-build route below remains the primary path if any gate fails.

## Implementation sequence

1. **Runtime contract.** Use the included engine in the app with no user-facing engine selection. The core accepts an explicit independent `wine` path for CLI tests, checks that executable `wine` and `wineboot` files sit together, and rejects CrossOver paths. Its diagnostic probe runs `wine --version`, records the executable's file description and whether sibling `wineserver` exists, and times out after ten seconds. This is a command check, not full runtime verification. Add dependency probes with actionable errors; never silently fall back to CrossOver or to `~/.wine`.
2. **Build prototype in isolation.** The [Wine 11.0 source experiment](WINE_BUILD_EXPERIMENT.md) pinned the source, validated an x86_64 compiler/Rosetta path on Apple Silicon, built project-local Bison and x86_64 FreeType, and completed local build/install for both PE architectures. `wine --version`, disposable prefix initialization, tiny x86_64/i686 Windows console programs, and a self-authored quiet MSI install ran. The [development package](LOCAL_WINE_RUNTIME.md) gives the loader relocatable FreeType plus pinned Mono/Gecko and initialized fresh Caskrun bottles without caller overrides. A separate upstream GnuTLS build removed a controlled ECDSA signature error and the observed Steam certificate-check errors without weakening verification. The [Steam follow-up](STEAM_SMOKE.md) reached two connection managers; its supervised updater finished both stages on retry and reached a logged credentials-waiting state. A fresh upstream source build with pinned Steam CEF/Dock patches and source receipts is now in the local development package. Repeat the live Steam UI and Dock test from that package, then complete dependencies for games and validate actual use before calling the runtime usable. Wine's README documents the `configure`/`make`/`make install` flow; ARM Homebrew libraries cannot satisfy this x86_64 build. [Wine source README](https://github.com/wine-mirror/wine/blob/master/README.md)
3. **Bottle lifecycle.** For each bottle set an absolute `WINEPREFIX` inside Caskrun's data directory. The core runs sibling `wineboot --init` before first launch, bounds the wait to 120 seconds, waits briefly for the registry file, and records the chosen Wine path. This passed fake-runtime tests and fresh-bottle smokes with the relocated development Wine wrapper and local Mono/Gecko, without caller overrides. Next persist runtime version/architecture with the bottle and interpret startup errors. A directory or one registry file alone is not evidence of a healthy prefix.
4. **Smoke tests on Apple Silicon.** Disposable-prefix `wine --version`, `wineboot --init`, self-authored x86_64/i686 EXEs, and MSI tests have run. Valve's Steam installer and updater ran. An earlier packaged app showed a black Steam sign-in; a later disposable patched-Wine prototype showed a usable sign-in and working Steam Dock focus. The migrated development app/DMG still needs its live Steam UI check. Steam account sign-in, a game launch, update rollback, uninstall, and `wine notepad` remain. Record install, launch, login, update, and game outcomes separately. The x86_64 Wine binary uses Rosetta on this Apple Silicon Mac; Intel Mac hardware testing is not required. [Apple Rosetta documentation](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)
5. **Release packaging.** The current self-contained DMG is a local, ad-hoc signed development artifact with source and patch receipts. Before public release, produce a versioned Developer ID signed and notarized app/runtime, verify the complete dependency tree, Gatekeeper result, source provenance, SHA-256, and license/notice manifest, and add rollback so an update cannot silently alter existing bottles. Wine and the two Caskrun Wine patches are LGPL-2.1-or-later; distribute the license and corresponding source/changes according to that license, and review every additional library independently. [Wine license](https://github.com/wine-mirror/wine/blob/master/LICENSE)

## Apple Silicon horizon

The first route is an x86_64 Wine binary translated by Rosetta on Apple Silicon, while Caskrun's own Swift/Rust processes remain native ARM64. Apple says macOS 27 is the final general-purpose Rosetta release; after that, only a limited subset remains for older gaming titles. This x86_64 Wine runtime is therefore a **short-term bridge**, not our long-term Apple Silicon strategy. [Apple's September 2026 notice](https://developer.apple.com/news/?id=w5ngl9k2)

Native ARM64 Wine alone does not establish that x86/x64 Windows apps such as Steam run. They also need an x86 translation route. CodeWeavers' July 2026 ARM64 preview uses a custom macOS FEX port and reports substantial limitations; that is evidence of feasibility, not a reusable Caskrun runtime. Upstream FEX currently rejects macOS in its build configuration. Track a genuinely open, independently buildable macOS x86 translation path as a separate research milestone and do not claim it is implemented. [CodeWeavers ARM64 preview](https://www.codeweavers.com/blog/mjohnson/2026/7/31/crossover-preview-the-right-to-bear-arm64-on-mac), [upstream FEX platform check](https://github.com/FEX-Emu/FEX/blob/main/CMakeLists.txt)

**Exit criterion for the first usable runtime:** an independently sourced Wine build passes disposable-prefix EXE/MSI smoke tests, starts through Caskrun without diagnostic overrides, resolves its complete dependency set from a relocatable signed package, reports installer completion, and can be reproduced from pinned sources. The narrow MSI, FreeType, Mono/Gecko, ECDSA, and disposable Steam CEF/Dock checks passed in their tested packages, but the full criterion is **not met**: the current packaged Steam live UI, updater reliability across fresh bottles, account sign-in, games, media/graphics/controller dependencies, and release signing still need validation. Catalog compatibility must be recorded per app rather than inferred from Wine's presence.
