# Steam on the independent Caskrun runtime: installer and TLS smoke tests

_23 September 2026. Apple Silicon Mac; Caskrun app/core are ARM64, and the independently built x86_64 Wine 11.0 package runs through Rosetta. This is a development test, not a Steam compatibility rating._

## Installer provenance and scope

Valve's [official Steam download page](https://store.steampowered.com/about/) originally linked to `https://cdn.akamai.steamstatic.com/client/installer/SteamSetup.exe` during the first smoke; on 23 September 2026 it linked to `https://cdn.fastly.steamstatic.com/client/installer/SteamSetup.exe`. Both URLs supplied the same tested file, identified locally as a PE32 Windows GUI executable using a Nullsoft installer. Its SHA-256 was `7d3654531c32d941b8cae81c4137fc542172bfa9635f169cb392f245a0a12bcb`. Valve did not publish a checksum in the page we checked; this hash identifies the bytes tested, rather than proving an upstream signature.

The initial runs used fresh Caskrun bottles under `.build/steam-probe/` and a clone of the independent development Wine package. The later TLS comparison used a cloned Steam prefix and a separately built Wine/GnuTLS package under `.build/tls-validation/`. Runs had **no caller-set DYLD paths or `WINEDLLOVERRIDES`**. The packages include Wine 11.0-pinned Mono and Gecko installers. No CrossOver files or runtime were copied, and no Steam account or credentials were used. The test did not install anything into `/Applications`.

## What happened

| Stage | Observed result |
| --- | --- |
| Interactive `SteamSetup.exe` via Caskrun `launch-wait` | Direct Wine process was still running at the 90-second test timeout and was stopped. No `Steam.exe` had been installed. No UI action was taken, so this result does not identify a compatibility failure. |
| Fresh-bottle `SteamSetup.exe /S` via `launch-wait` | Direct Wine process exited 0 in about 2 seconds after prefix startup. `drive_c/Program Files (x86)/Steam/Steam.exe` and `uninstall.exe` existed inside the bottle. |
| First launch of installed `Steam.exe` | Steam downloaded its updater package and logged `Update complete, launching Steam...`. The direct Wine process exited 42 while child processes continued; this is why a single process exit cannot be reported as completed Steam startup. |
| Continued updater run | The subsequent bootstrap log recorded more downloads and extraction, then started the updated `steam.exe` and several `steamwebhelper.exe` processes. `cef_log.txt`, `steamui_html.txt`, and `webhelper.txt` were created. The latter records a `DesktopLoginWindow` and a browser window creation request. |
| Initial sign-in connectivity | `steamui_login.txt` reached `WaitingForCredentials`, but no credentials were entered. `console_log.txt` repeatedly reported `Crypto API failed certificate check, error flags 0x00000008` for Steam connection managers, and the client logged `LogonFailure No Connection`. The client also reported Chrome/ANGLE graphics and network warnings. |
| Independent GnuTLS retest | A separate Wine 11.0 build with project-built x86_64 GnuTLS produced **zero** certificate-check errors in the new `console_log.txt`. `connection_log.txt` recorded a WebSocket connection manager `ConnectionCompleted()` and `[Connected]`, then a remote `Try another CM` / `Failure` response. Steam automatically connected to a second manager before this bounded run ended. Steam still reported `LogonFailure No Connection`; no account sign-in was attempted. The logs do not establish a persistent connection failure. |

## Automatic recipe in the self-contained development app

The new original `install-catalog steam` core command was run from the ARM64 Caskrun.app bundle with its included GnuTLS-enabled Wine engine and a disposable `CASKRUN_HOME` under `.build/steam-recipe-smoke/`. The caller removed DYLD and Wine path variables and `WINEDLLOVERRIDES`. It fetched the current Valve-linked Fastly installer over HTTPS with bounded size/time, checked PE architecture, recorded the SHA-256 above, created a fresh Steam bottle, ran `SteamSetup.exe /S`, found `Steam.exe`, saved a Steam launcher, and returned a spawned updater process and install log. The bottle and launcher are visible through the core's `apps` command. This verifies the **automatic core path** through launcher creation; a later SwiftUI test against Caskrun user data exposed a separate installer stall described below.

The new bottle's updater log began downloading the roughly 336 MB client update, then stopped after about 70 MB without an explicit error or completion marker. No Wine/Steam process remained at the next check. A supervised continuation in **the same bottle** kept the shell alive and restarted its saved Steam launcher. Its 32-bit updater resumed and completed 290,611 KB, then handed off to a new Steam process. That process fetched the 64-bit `steam_client_win64` manifest but spent more than three minutes at `Add pending download` for `bins_win64.zip...`, with no package download progress or connection-manager log. The exact CDN package URL returned HTTP 200 from macOS, and Steam had established CDN TCP sockets; this does not identify the Wine/client-side cause. After the 270-second bound, only this disposable bottle's Wine server was stopped. Neither run demonstrates a finished updater, a visible login screen, sign-in, game download, or play. Supervision also shows that the first short-lived CLI session was insufficient evidence of a Wine startup failure.

A later bounded retry in that **same bottle** downloaded the full 236,054 KB 64-bit update in about 24 seconds and logged `Update complete, launching Steam...`. The client then reached `WaitingForCredentials`, requested a `DesktopLoginWindow`, passed a connectivity test, and connected to a WebSocket connection manager. The new run recorded zero certificate-check or `LogonFailure No Connection` messages. No credentials were entered, and the window was not visually verified. The earlier download stall was **not reproducible** in this retry; its cause remains unknown. Only this disposable bottle's Wine server was stopped at the end of the bound. A repeat fresh-bottle test and updater progress timeout with retry/resume are still needed.

## Live SwiftUI install and recovery test

The **Set up Steam** action in the running Caskrun app created a Caskrun-owned user-data bottle. Two `SteamSetup.exe /S` attempts with the same official installer stalled around SteamService and reached the five-minute installer timeout. The older build left Wine child processes running after the direct process timed out; they were stopped through Caskrun's prefix-specific quit operation. The presence of `Steam.exe` did not make either setup a success. Its partial bootstrap file was checked and was a valid 32-bit PE.

A separate fresh bottle under `.build/steam-space-probe/Application Support/` completed `/S` with those same installer bytes in about 1.8 seconds. A space in the bottle path alone therefore does not explain the user-data stall. A supervised launch of the partial `Steam.exe` in the failed user-data bottle downloaded the 32-bit and then 64-bit updates; its logs reached `WaitingForCredentials`, recorded a `DesktopLoginWindow` as created and unhidden, and connected to a WebSocket connection manager. This was log and process evidence, **not** a visually confirmed login window or working sign-in.

The current source adds guarded same-bottle recovery for this exact timeout case: it checks that the prefix is idle and the Steam bootstrap is a valid PE before skipping the stalled installer step, and it stops bottle-specific Wine processes on a new timeout. Focused tests pass. The rebuilt core recovered this same failed bottle without rerunning `SteamSetup.exe`, saved a launcher, and returned an explicit recovery note. After reopening the packaged app, Home showed **Steam**; clicking **Open** started Steam and its webhelpers. This verifies the Home launcher path, while recovery through SwiftUI's **Retry setup** action still needs testing. The cause of the SteamService stall remains unknown. No credentials or game were used.

## Black-window and Dock investigation

An earlier packaged build gave the user a black Steam window and two Dock entries named **Wine**. Steam's baseline CEF log included a DXGI adapter-driver query failure and a GLES 3 request where the reported maximum was GLES 2. In a cloned disposable prefix, launching Steam with `-cef-disable-gpu` propagated `--disable-gpu` and `--disable-gpu-compositing` to its web helpers and removed those particular initialization errors. Caskrun applies this flag only to the initial recipe launch and a saved Steam launcher whose installed receipt and executable path match; focused tests verify other EXEs receive no flag. The client still logged a created/unhidden `DesktopLoginWindow` and `WaitingForCredentials`. The user confirmed that the sign-in window **remained black** in that earlier packaged build, so the flag alone was insufficient. [Valve's issue tracker](https://github.com/ValveSoftware/steam-for-linux/issues/10561) also records it as a workaround for some black-window cases, not a universal fix. Small evidence remains at `.build/research/steam/cef-disabled-gpu-20260923.txt`; the cloned prefix was moved to Trash.

A later disposable Steam test injected `--in-process-gpu --disable-gpu` directly into Steam's web helper command line while keeping CEF sandboxing enabled. The user confirmed that its sign-in window was visible and usable for more than two minutes. Replacing the web helper itself is not an update-safe solution because Steam repairs that file, so the temporary wrapper and its updater pause are **not** in the packaged app. An original, Steam-only Wine process-creation patch now adds those arguments only when Steam launches its web helper; the current packaged process list confirmed them on a real helper. The exact test sequence is retained at `.build/research/steam/cef-in-process-gpu-20260923.txt`. No credentials were entered or game launched in this test.

Upstream Wine's macOS loader identifies itself as **Wine**, and its macOS driver promotes each visible Windows GUI process to a regular Dock application. Steam and `steamwebhelper.exe` are separate processes, explaining why two Wine-labeled Dock entries can appear without two Steam launch requests. Read-only local inspection found that CrossOver creates a separate Steam.app with a Steam name/icon and uses a different Wine loader path; Caskrun has not copied its helper or code. A CodeWeavers staff member also [described separate Steam and steamwebhelper Dock icons](https://www.codeweavers.com/support/forums/general/?forumcurPos=100&msg=279837&t=27) on an older CrossOver build. An original Wine macOS identity patch now makes `steam.exe` accessory and its visible web helper the single Steam-named Dock application with a PE-derived Steam icon. The user later confirmed one Steam Dock icon that restored focus in the packaged app; repeatability across relaunches remains unverified. [Wine loader plist](https://gitlab.winehq.org/wine/wine/-/blob/wine-11.0/loader/wine_info.plist.in), [Wine macOS app driver](https://gitlab.winehq.org/wine/wine/-/blob/wine-11.0/dlls/winemac.drv/cocoa_app.m).

## Current packaged launch and runtime transition

The local DMG now includes a fresh upstream Wine 11.0 build with the reviewed CEF and Dock patches, source archive, patch receipts, and notices. Its complete runtime-tree SHA-256 matched the pinned approved build after packaging. Before opening the existing Steam launcher, Caskrun required the exact recorded TLS-only predecessor and approved successor identities, a verified installed Steam receipt and launcher, and an idle bottle. It retained the old runtime record, migrated this one Steam bottle, and then performed normal prefix verification. No other bottle or custom Wine path is eligible for this transition. A separate APFS clone of the idle bottle was retained under ignored `.build/recovery/` before this run.

The packaged Home icon launched `steam.exe` and `steamwebhelper.exe`. The live helper command line contained `--in-process-gpu --disable-gpu`, and the newest Steam login log reached `WaitingForCredentials` and requested a connection. Subsequent user-led checks confirmed a visible, usable sign-in window and a single Steam Dock icon that restored it, but other relaunches were black before recovering. The user also reported low visual quality. No account sign-in or game was tested.

A later read-only check found `LogPixels=0x60` (96 DPI) and no Wine `RetinaMode` in that live bottle. Steam's renderer was running with `--device-scale-factor=1`, and an earlier CEF report measured a 1512 × 982 display at scale 1 while the Mac's built-in Retina panel is 3024 × 1964 pixels. This is a plausible explanation for the soft image, not proof of a rendering fix. The active bottle was not changed; compare 96 and 192 DPI in a separate idle test bottle before choosing a default. The logs confirm that the sign-in window was created, but do not explain intermittent black pixels.

The installed Steam executable's extracted ICO contains 13 images, including a 256 × 256 PNG. AppKit decodes all 13 and selected that large representation for Home's 48-point Steam icon; a 96-pixel Retina render was crisp. Discover's separate publisher artwork also has a 256 × 256 image. This read-only audit found no icon-extraction defect. Steam's 1× CEF window is a separate display issue.

A later read-only UI smoke opened the verified development DMG while the existing Steam process remained running from the older app bundle. The packaged Home displayed Steam's saved icon, and Bottles displayed the same Steam bottle, its actions, Wine tools, graphics availability, and the bottle's unchanged 96 DPI status. ## Dependency clue and controlled certificate check

A **read-only** inspection of the installed CrossOver bundle's linked library names found x86_64 `libgnutls.30.dylib` beside its Wine crypto backend. This was a dependency clue only; Caskrun did not launch or copy CrossOver code, assets, recipes, or runtime. Our GnuTLS, GMP, Nettle, and Wine binaries were built separately from upstream source in the Caskrun project.

To test the suspected crypto gap without Steam, we generated a local self-signed P-256 ECDSA certificate and verified it through Wine's Windows certificate APIs. The original package returned `verify=0`, `chain_status=0x28` (the expected untrusted test root plus an invalid-signature flag). The independently rebuilt Wine/GnuTLS package returned `verify=1`, `chain_status=0x20` (only the deliberately untrusted test root). A relocated copy gave the same result without caller library paths or overrides. This supports a real signature-verification fix, but does **not** prove which certificate algorithm Steam used. Certificate validation was never disabled.

The earlier login-window evidence came only from Steam's logs and process list because the available macOS UI control did not expose Wine's unbundled windows. The later user-led visual checks are encouraging but do not establish reliable relaunches. No account sign-in, library loading, game installation, launch, graphics mode, controller, or update rollback was tested. The 64-bit updater stalled once and completed on a later retry; the earlier connection-manager response does not establish a persistent failure. The later live SwiftUI install also timed out twice around SteamService, independently of the updater result. The live Steam bottle currently reports Wine Retina mode off and 96 DPI; the new per-bottle High Resolution Mode passed an off → on → off test in a disposable Wine bottle, but its effect on Steam's clarity and black-window behavior is unverified.

The development logs and generated bottles are retained under ignored `.build/steam-probe/`, `.build/tls-validation/`, and `.build/steam-recipe-smoke/` for diagnosis. The disposable path-with-spaces bottle was moved to Trash after copying its logs to `.build/research/steam-space/`; the live SwiftUI bottle is under Caskrun's user-data directory. The [feature inventory](FEATURES.md) keeps Steam at partial/untested compatibility until sign-in and real use can be verified.
